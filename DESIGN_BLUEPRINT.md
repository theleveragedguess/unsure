# Design Blueprint: Probabilistic Calculation Engine

## 1. Core Architectural Patterns

The primary architectural style is a **Modular Pipeline** combined with a **Monte Carlo Simulation Engine**. The system parses a domain-specific language (DSL) into an Abstract Syntax Tree (AST), which is then evaluated repeatedly to generate a stochastic distribution of results.

### Primary Design Patterns

1.  **Interpreter Pattern**: This is the core pattern used for evaluating the parsed expressions. The `petitparser` library creates an AST (Abstract Syntax Tree) representing the mathematical formula. Each node in the AST (`AstNode`) implements an `emit()` method, which serves as the interpreter's evaluation function.
2.  **Composite Pattern**: The AST is a classic implementation of the Composite pattern. Abstract classes like `MathOperationNode` and `MathFunctionNode` treat individual values (`NumberNode`) and complex sub-expressions identically.
3.  **Strategy Pattern**: The `Calculation` class accepts a `Formula` typedef (`double Function()`). This allows the injection of arbitrary calculation strategies, either generated by the parser or provided directly as Dart code (e.g., compounding interest functions).

## 2. Interfaces and Data Structures (I/O)

### Input Structures
*   **`String` (DSL)**: The primary input is a string representing a mathematical expression with probabilistic ranges (e.g., `"10~20 * 42"`).
*   **`Formula` (typedef)**: A zero-argument function returning a `double`. This serves as the executable input for the calculation engine.
*   **`AstNode`**: The base interface for the parsed expression tree.
    *   *Method*: `double emit()` - Generates a single deterministic or stochastic value.
    *   *Property*: `bool isStochastic` - Indicates if the node has randomness.
*   **`Range`**: Represents a normal distribution defined by a minimum and maximum (representing the 95% confidence interval). Uses a generator (`Iterable<double>`) based on the Box-Muller transform.

### Output Structures
*   **`Result`**: The primary output data structure encapsulating the findings of the Monte Carlo simulation.
    *   *Statistical Data*: Contains a `Statistic` object (from `t_stats` package) detailing mean, standard deviation, etc.
    *   *Confidences*: Lists of `Confidence` objects detailing ranges for specific probability thresholds (e.g., 95%, 99.7%).
    *   *Percentiles*: A list of `double` representing the 0th to 100th percentiles of the generated distribution.
    *   *Histogram*: A `ProbabilityHistogram` summarizing the distribution into bands for visualization.

## 3. Evaluation for Financial Time Series Data

### Strengths
*   **Monte Carlo Simulation**: The core methodology (running a calculation hundreds of thousands of times to find a distribution) is highly applicable to financial forecasting (e.g., Value at Risk (VaR), option pricing).
*   **Box-Muller Transform**: The `Range` class uses a robust algorithm for generating normally distributed variables, which is a standard assumption in many foundational financial models (like Black-Scholes).
*   **Confidence Intervals**: The built-in generation of confidence intervals aligns perfectly with risk assessment reporting.

### Limitations & Inefficiencies
*   **Lack of Temporal Dimension**: The current model evaluates a static formula. Financial time series data requires sequential state transitions (e.g., $S_{t+1} = S_t \cdot e^{\dots}$). Simulating paths over time would require executing independent `Calculation` instances sequentially, which is inefficient and loses path-dependency context.
*   **Memory Overhead for Large Simulations**: The `Calculation.run()` method stores every iteration's result in a list (`List<double>.generate(iterations, ...)`). For deep time series simulations (e.g., 10,000 paths $\times$ 252 trading days), storing all intermediate values to calculate distributions would cause significant memory pressure. A streaming statistical accumulator would be more efficient.
*   **Independent Variables Assumption**: The current `AstNode` evaluation assumes all variables are independent. Financial models often require correlated random variables (e.g., simulating multiple correlated asset prices).
*   **Performance Bottlenecks**: The AST evaluation (`emit()`) uses dynamic dispatch extensively. While Dart is fast, compiling the AST to a tight, vectorized loop or a direct machine code representation would significantly accelerate large-scale financial simulations.

### Conclusion for Synthesized Library
To adapt this methodology for a financial time series library, the engine must evolve from evaluating *static expressions* to evaluating *stochastic differential equations (SDEs)* over discrete time steps. The simulation engine should be refactored to use vectorized operations and streaming statistics to avoid massive memory allocations, and the DSL must be expanded to support time indices and correlated variables.
